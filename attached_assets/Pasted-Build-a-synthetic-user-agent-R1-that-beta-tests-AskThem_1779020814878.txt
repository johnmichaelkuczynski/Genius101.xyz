Build a synthetic user agent ("R1") that beta-tests AskThem end-to-end. R1 must produce raw, reviewable evidence of every interaction — not pass/fail summaries.
NON-NEGOTIABLE REQUIREMENTS (read first)
These are the parts a previous synthetic-user build for a different app failed on. If any are missing, the deliverable is rejected.

No green-checkmark theater. R1 does NOT produce a summary that says "Function 3: PASS." R1 produces raw evidence: the exact text R1 typed, the exact text the app returned, the exact network responses, the exact screenshots. The judge's critique is a paragraph of prose, not a boolean. "PASS/FAIL" exists only as a filter for failures.md — never as a substitute for the evidence itself.
The HTML report must be reviewable by a human in under 30 minutes. Every interaction shows, in order: what R1 was trying to test, what R1 typed (the actual string), what the app returned (the actual response body), the screenshots, and the judge's prose critique. No collapsed sections. No "Click to expand details." Everything visible.
The live view must show R1's actual inputs and the app's actual outputs as they happen — not "Step 4 of N in progress." See "Live view" below.
Network traffic must be captured raw. Every request to /api/* and its response body goes into network.log as JSONL. Not summaries. Actual JSON.
Three screenshots per interactive step (before R1 acts / after R1 types / after the app responds). For read-only / navigation-only steps, one screenshot is fine. The sanity check at the end must distinguish these two cases and NOT flag legitimate single-screenshot navigation steps as failures.
If R1 cannot complete a step, the failure is logged with the actual error, the page HTML at the moment of failure, and a screenshot. R1 does NOT skip and mark green.
Per-step API-call expectations are route-specific, not boolean. A step like "ask a question" must expect POST /api/chat specifically, not "any /api/* call." A step like "upload thinker text" must expect POST /api/admin/thinkers/:id/upload-text. The sanity check verifies the specific route fired. Boolean checks are forbidden — they allow steps to satisfy themselves with unrelated background requests.
Critical button clicks are wrapped in Promise.all([page.waitForResponse(predicate), click]) so R1 doesn't silently advance when a click fails to fire its expected request.
AskThem's most important invariant is anti-hallucination: every quote in a chat response must be verifiable against the database. R1's judge model must explicitly check this on every chat response. If a response contains a quoted passage that isn't present in the thinker's actual thinker_quotes rows (verifiable via the admin API), that's a CRITICAL INVARIANT VIOLATION, not just a judge concern.

Architecture

Browser automation: Playwright (Node, single-file tools/r1/run.mjs). Standalone Node project, not in any workspace.
R1's brain: Anthropic API. Model: claude-opus-4-7. Key in ANTHROPIC_API_KEY.
Judge: Separate Claude API call per interaction. Returns prose critique, not a verdict. Judge has database read access for the quote-verification invariant (described below).
Live view: Local HTTP server on port 7777. Plain node:http, zero extra deps.
Target app: AskThem running locally. Frontend port from vite.config.ts; API on the same origin (single Express server serves both). R1 must accept APP_URL as a config knob; default to http://localhost:5000 and document how to override.

What R1 is testing — the AskThem functions
Per the blueprint, AskThem has these core functions. Run each in order. Skip nothing unless SKIP_FUNCTIONS lists it.
Function 1 — Chat with a single thinker
This is the heart of the app. R1 must exercise it broadly.
For each of at least 4 thinkers available in the database (R1 fetches the list via GET /api/thinkers):

Open the chat page for that thinker.
Send a substantive philosophical question relevant to that thinker (e.g., for Plato: "What is the role of the Forms in your epistemology?"; for Freud: "How do you distinguish repression from suppression?"). R1's brain composes a fitting question for each.
Expected route: POST /api/chat (or whatever the streaming endpoint is — verify against the blueprint and code).
Verify the response streams (Playwright sees the stream via page.on('response') for SSE or via DOM mutation observation).
Capture the final assembled response text.
Capture any inline citations / quoted passages in the response.

For each chat response, the judge must:

Critique whether the response is in-voice and substantive.
Run the quote-verification invariant (described below).
Flag whether the response speaks AS the thinker (correct) or ABOUT the thinker (incorrect — AskThem's whole point is first-person voice per the blueprint).

Also test:

A question outside the thinker's expertise / time period, to see if the response stays in-character without inventing.
A deliberately leading question that invites the thinker to contradict their known positions, to see if the response holds the line.
A very short question ("why?").
A very long question (~500 words of context).

If no matching row exists, that's a CRITICAL INVARIANT VIOLATION.

The quote-verification invariant (detail)
This is AskThem's defining feature and the thing R1 must enforce hardest.
For every chat response, the judge does:

Parse the response text for quoted passages (anything in quotation marks of meaningful length, say ≥ 15 chars).
For each quoted passage:

Query GET /api/admin/thinkers/:thinkerId/quotes?search=<first words> to look for a match.
Also query GET /api/admin/thinkers/:thinkerId/chunks?search=<first words> because the response might cite source text not yet extracted as a discrete quote.
If neither returns a near-match (judge uses fuzzy comparison: lowercase, strip punctuation, allow ±2 word differences), the quote is unverified.


Record each unverified quote in the interaction's invariant_violations field with: the quote text, the thinker id, the queries the judge ran, and the empty results.

Unverified quotes = CRITICAL INVARIANT VIOLATIONS in failures.md. This is non-negotiable.
R1's behavior
R1 is a single generic synthetic user with admin privileges. For each interaction, R1 picks one of these approaches and logs the choice with reasoning:

Substantive question in the thinker's wheelhouse
Leading question inviting contradiction of known positions
Out-of-period / out-of-expertise question
Minimum viable input (one word)
Very long contextualized question (~500 words)
Probe a known constraint (ask the thinker to step out of voice — they shouldn't)
Trigger a feature path (ask for a specific quote to test retrieval)
Plausibly-wrong / malformed input

R1 picks based on what will best probe that specific feature.
Typing constraint: No clipboard paste. Use Playwright .type() with TYPE_DELAY_MS=15 so the live view can show keystrokes building up.
Per-interaction flow
For each step:

Navigate / open relevant UI.
Capture page state.
Send to R1 brain: "Here is the step and current state. Pick an approach. Briefly explain why. Then produce the input."
Take "before" screenshot.
Type input.
Take "typed" screenshot (await element value matches typed input).
Wrap critical button clicks in Promise.all([page.waitForResponse(predicate), click]) with the predicate matching the expected route.
Wait for full response (handle streaming — accumulate stream chunks; final response is the assembled stream).
Take "after" screenshot.
Capture response body, console errors, SSE events.
For chat interactions: run the quote-verification invariant via the judge.
Send full interaction to judge: "Critique functionally and qualitatively. Was the response in-voice? Did it stay first-person? Did all quotes verify against the database? Anything broken, off, slow, or off-character?"
Append to transcript; stream summary to console; update live-view state.
